# Windows 11 でホットキーを使用しているアプリを調べる手順の検証記録

[手順書](../windows-hotkey-conflict.md)・[参考資料](../reference/windows-hotkey-conflict.md)・[ロールバック](../extra/windows-hotkey-conflict.md)

## 対象と検証環境

- **目的**: Hotkey Screener で、指定したホットキーを使用しているアプリを調べる手順を、登録状態の分かるテスト用アプリで確認する
- **状態**: **Windows 11 の実機で、テスト用アプリの使用アプリ検出を確認済み（2026-10-11、JST）**
  - 初回準備の手順 1〜3 と、実施手順の手順 1〜4 に対応する、ZIP の取得・展開・署名確認、起動、対象行の検出、プロセス ID と実行ファイル名の照合を行った
  - ウィンドウに関連付けた登録と、ウィンドウを持たないスレッドの登録の両方で、既知の所有アプリと表示が一致した
  - Hotkey Screener とテスト用アプリを通常終了し、試験用の登録が解除されたこと、解除後に一覧から消えることを確認した
  - 任意の登録可否プローブは、今回掲載する版を Windows PowerShell 5.1 で実行し、登録保持中の `1409` と解除後の `-1` を確認した。掲載した PowerShell の 5 ブロックは構文エラー 0
  - 実施手順の手順 5 の実際のアプリ設定の変更と復旧、Program Files への配置、使用アプリが分からない場合の切り分けは実施していない
- **今回の確認方法**: テスト用アプリが `RegisterHotKey` で保持するキーと既知のプロセスを、Hotkey Screener の表示と照合した。キーの登録、検出、解除後を分けて記録した

## 実施前の状態

- 制御試験の開始時に、テスト用アプリで Ctrl+Alt+Shift+F10 をウィンドウに、Ctrl+Alt+Shift+F9 を別スレッドに登録した
- 2 登録とも成功し、所有プロセスは `HotkeyFixture.exe`、PID `40004` と分かっていた
- Ctrl+Alt+Shift+F8 はテスト用アプリでは登録せず、登録可否プローブでも登録可能だった
- この既知の状態を使い、所有アプリを検出できることと、登録解除の前後の違いを比較した

## 完了時点の状態

- テスト用の 2 キーは、いずれも `HotkeyFixture.exe (PID: 40004)` と表示された
- 検出はユーザー本人が操作し、返信と画面の両方で表示を照合した
- 検出時にテスト用アプリの `WM_HOTKEY` の処理ログは増えなかった
- テスト用アプリのウィンドウ登録とスレッド登録はどちらも解除成功。プロセスの終了も確認した
- 解除後の Ctrl+Alt+Shift+F8 / F9 / F10 は、掲載プローブでいずれも `-1`（登録成功・解除済み）が各 2 回返った
- 解除後に起動し直した Hotkey Screener の一覧には、上記の 3 キーはなかった
- 最後の確認用の Hotkey Screener も通常終了し、Hotkey Screener とテスト用アプリのプロセスはともに 0 件だった

## 付録: 配布物と画面の確認（2026-10-11）

### 初回準備 / 手順 1〜3: ZIP と署名

- 公式配布の `HotkeyScreener.zip` を取得して展開した
- ZIP の SHA-256 は `EE7302A37C31CFD1AB10642597E3AB5103F665E829E668D303B171933DB4C2EA`
- ZIP の内容、実行ファイルの版、署名の結果は[検証環境](#対象と検証環境)の表の範囲
- 署名は PowerShell の `Get-AuthenticodeSignature` で確認した。プロパティ画面での確認は実施していない
- `hkscr.exe` の起動と動作は確認していない

### 実施手順 / 手順 1〜4: 起動と検出

- `hkscr64.exe` を通常権限で起動すると、テスト用の 2 登録を含む `199 hotkeys in use` が表示された
- 一覧の列は `Key Combination` と `Application`
- 対象行の `Application` 列にある `Click to detect application` を使って検出する画面だった
- 通常権限で検出を試すと、`Restart as Administrator?` が表示された
- ユーザー本人が要求を確認・承認し、管理者として再起動した
- 管理者として開いた窓には自動操作で入力できなかったため、対象 2 キーの検出はユーザー本人が各 1 回行った
- 使用アプリの表示は、次の[テスト用アプリとの照合](#付録-テスト用アプリとの照合2026-10-11)で確認した

## 付録: テスト用アプリとの照合（2026-10-11）

### 実施手順 / 手順 2〜4: 既知の登録と表示の一致

テスト用アプリの登録結果と、Hotkey Screener の表示を照合した。

| キー | テスト用アプリの登録 | Hotkey Screener の表示 | 結果 |
|---|---|---|---|
| Ctrl+Alt+Shift+F10 | ウィンドウハンドル `5701960` に関連付けて登録。登録 `True`、エラー `0` | `HotkeyFixture.exe (PID: 40004)` | 既知の所有者と一致 |
| Ctrl+Alt+Shift+F9 | 別のスレッド `34300` で、ウィンドウハンドルを `NULL` にして登録。登録 `True`、エラー `0` | `HotkeyFixture.exe (PID: 40004)` | 既知の所有者と一致 |
| Ctrl+Alt+Shift+F8 | テスト用アプリでは登録なし。掲載プローブで `-1`（登録成功・解除済み） | 最終確認の一覧には行なし | 登録されていない状態を確認 |

- `NULL` の登録を検出できたことは、今回のテスト用アプリ・実機・版の範囲の結果
- 今回の 2 キーの検出で、テスト用アプリの `WM_HOTKEY` の処理ログは増えなかった
- ほかのアプリのホットキー検出時にも操作が発火しないことまでは確認していない

## 付録: 終了と解除の確認（2026-10-11）

### 実施手順 / 手順 6・ロールバック / 手順 2

- ツールを終了する操作は[ロールバックの手順 2](../extra/windows-hotkey-conflict.md#ロールバック)にも対応する
- 検出後に、テスト用アプリの読み込んだモジュール一覧を確認した範囲では、Hotkey Screener の DLL は見つからなかった
- この確認はテスト用アプリ 1 プロセスの範囲。全プロセスから DLL やフックが解放されることの保証ではない
- ユーザー本人が管理者として開いた Hotkey Screener を閉じた後、`hkscr` / `hkscr64` のプロセス件数は 0 だった
- この時点ではテスト用アプリの PID `40004` は稼働中だった。読み込んだモジュールのうち `*hkscr*` に一致するものは 0 件だった
- テスト用アプリに終了指示を渡して通常の `Close` を行った。ログの `02:26:26`（JST）に、ウィンドウの登録解除 `True`、スレッドの登録解除 `True`、アプリの終了が記録された。`WaitForExit` も `True` だった
- 解除後に通常権限で Hotkey Screener を起動し直すと、`197 hotkeys in use` が表示された
- 画面では通常キーの区分が F4 の次に F11 となり、F8 / F9 / F10 の行が無いことを確認した。使用アプリの再検出は行っていない
- 最後の確認用の Hotkey Screener は、窓の × で通常終了した。最終確認では Hotkey Screener とテスト用アプリのプロセスはともに 0 件だった

## 付録: 任意の登録可否プローブの確認（2026-10-11）

### ホットキーの登録可否を確認する（任意） / 手順 1〜3

通常権限の Windows PowerShell `5.1.26100.9444` で、今回の手順書のコードを確認した。

| キー | Hotkey Screener の稼働中・登録保持中 | Hotkey Screener の終了後・登録保持中 | テスト用アプリの終了・登録解除後 |
|---|---|---|---|
| Ctrl+Alt+Shift+F10 | `1409` を 2 回 | `1409` を 2 回 | `-1` を 2 回 |
| Ctrl+Alt+Shift+F9 | `1409` を 2 回 | `1409` を 2 回 | `-1` を 2 回 |
| Ctrl+Alt+Shift+F8 | `-1` を 2 回 | `-1` を 2 回 | `-1` を 2 回 |

- `1409` はすでに登録されている状態、`-1` はプローブによる登録成功と解除済みを示す
- 最終版の既定キー Ctrl+Alt+Shift+F10 でも、登録可能で解除済みと分かる表示を確認した
- `Add-Type` の読み込み済みを確認するガードを含め、同じセッションで再読み込みできた
- 掲載した PowerShell のコードブロック 5 個を構文解析し、エラーは 0 だった。構文解析だけのブロックを含み、切り分けの全操作を実行した結果ではない
- プローブの登録試験に対象キーの物理的な押下は使っていない
- このプローブの結果だけでは所有アプリを特定できない

## 付録: 現行の文書構成への適応（2026-10-11）

- Windows 初期設定へのリンクを「貼り付けの設定」の手順 1〜4へ更新し、ロールバックを `docs/extra/` へ分けた
- 出力を確認する PowerShell の 3 ブロックへ、反転表示の「確認」を追加した。登録・エラー取得・解除を行う C# の処理は変更していない
- 適応後の PowerShell の 5 ブロックを Windows PowerShell `5.1.26100.9444` で構文解析し、エラーは 0 だった
- 同じ PowerShell セッションで、掲載する Ctrl+Alt+Shift+F10 のプローブを 2 回実行した。どちらも `-1`（登録成功・解除済み）と、掲載する正常結果の日本語表示を確認した。`Add-Type` の再読み込みガードも通った
- 確認見出しの ANSI シーケンスが出力されることまで確認した。conhost の画面上での反転表示は、この適応時には確認していない
- 4 文書の相互リンク・アンカー 32 件と、主手順 6・初回準備 3・任意配置 4・切り分け 6・登録可否 3 の手順数を確認した
- この適応で Hotkey Screener の実機試験の範囲を広げていない

## 未確認の範囲

- 別の PC、別の Windows の版、別の Hotkey Screener の版
- 実際の常駐アプリの設定変更と、通常の操作の復旧
- Program Files へ配置する任意手順と、その配置による権限要求の変化
- 使用アプリが分からない場合の切り分け、設定を戻すロールバック
- リモート接続、別のログオンセッション、OS 再起動後の挙動
- 低レベルのキーボードフック、入力方式、アプリ内のキー割り当てによる入力処理
- 全プロセスの DLL・フックの解放
- 登録解除後の使用アプリの再検出。解除後は一覧に対象行が無いことまで確認した
