# 手順書の書き方

手順書・検証記録・参考資料・extra の書き方の規則。[AGENTS.md](../../AGENTS.md) の「文書を書く・直すとき」から案内する。書いたり直したりする前に読む。

## 手順書の構造

Windows 11・AlmaLinux 10 の実施手順は、既存・新規とも `docs/windows-setup.md`・`docs/almalinux-setup.md` を正本とする。個別ツール・VPN・リモート操作も、対応する OS のカテゴリの用途に集約する。AI コーディングエージェントの実施手順（導入・更新・共同作業・ブラウザ操作・Remote Control・GNOME 操作）は、両 OS とも `docs/ai-agents.md` を正本とする（2026-10-14 に、利用者の決定で2冊から分けた）。仮想マシン（VirtualBox・VirtualBox の bootc ゲスト・kvm-container・Hyper-V・VMware Workstation Pro・Windows Sandbox）は両 OS とも `docs/virtual-machines.md`、Forgejo のサーバーは `docs/forgejo.md` を正本とする（2026-10-15 に、利用者の決定で2冊から分けた）。同じ日に、利用者の決定で大きな項も2冊から分け、GNOME のリモート操作（デスクトップ共有・ヘッドレスセッション・リモートログイン）は `docs/gnome-remote.md`、WireGuard・Neovim・Samba（クライアント・サーバー）・Syncthing は両 OS とも `docs/wireguard.md`・`docs/neovim.md`・`docs/samba.md`・`docs/syncthing.md` を正本とする。シェルと端末（共通の bash 設定・シェルのツール・HackGen Console NF・WezTerm・Windows Terminal・Git Bash の設定・PowerShell 7 のプロファイル）も、同じ日に利用者の決定で2冊から分け、両 OS とも `docs/shell-terminal.md` を正本とする。正本を増やすのは、利用者の決定があるときだけにする。

- 設定・スクリプトの実装、開発用検査、macOS・他 Linux 固有の手順は元リポジトリに残す
- 検証・参考資料・ロールバックは元のファイルに保持し、用途の項のリードから案内する
- 集約後に案内だけとなった文書は削除する。旧パス・見出し・移動先を [集約対応表](consolidation-map.md) に記録し、旧原文は移動元コミットで確認する
- 2冊には AI エージェントの項・節を置かない。冒頭と `## 更新` のリードから ai-agents.md へ 1 行で案内する。AI エージェントの状態で分岐する手順だけは、その節の手順として残す（Remote Control のタスクは windows-setup.md、仮想モニターのドロップインは gnome-remote.md。後者は 2026-10-15 に almalinux-setup.md から移した）
- ai-agents.md は、OS で節を分けた手順書にする。`## 実施手順` が AlmaLinux 10、`## Windows 11 で使う` が Windows 11。後ろの節は、リードの最初の箇条書きに「対象: AlmaLinux 10」「対象: Windows 11」「対象: 両 OS」のどれかを書く
- virtual-machines.md は、OS でカテゴリを分けた手順書にする。`## AlmaLinux 10 で使う` と `## Windows 11 で使う` の下に、2冊と同じ `###` 用途 → `####` 手順を置く。forgejo.md は `## サーバー` の下に `### Forgejo` を置く。2冊には項を置かず、冒頭と `## 更新` のリードから 1 行で案内する
- gnome-remote.md・wireguard.md・neovim.md・samba.md・syncthing.md・shell-terminal.md も、virtual-machines.md と同じ形にする（gnome-remote.md は `## AlmaLinux 10 で使う` だけ）。2冊からは、冒頭・カテゴリ・`## 更新` のリードから案内する。冒頭には、全体の前提と、入れたものを上げる項を置く
- Windows の導入前の手順は `## Windows の導入`、bootc など別構成のゲストは virtual-machines.md の `## AlmaLinux 10 で使う` の用途に置く

### 2 冊の骨格（カテゴリ別）

2026-10-14 に、利用者の依頼で、2 冊の「実施手順」と任意節（必須・任意）の区別をやめ、カテゴリ別に組み直した。どの見出しも単独で通せるようにするため。旧→新の見出しと手順番号は[集約対応表の追補](consolidation-map.md#2-冊をカテゴリ別に組み直したときの追補)にある。ai-agents.md・extra・tool-catalog.md は、下の「各用途の手順は次の骨格に揃える。」のまま。

1. 見出しは `#` 題 → `##` カテゴリ → `###` 用途（ツール・主題）→ `####` 用途の中の手順。2 段の項があったもの（wireguard.md の「WireGuard: AlmaLinux 10 の PC からつなぐ」、virtual-machines.md の「VirtualBox: Windows 11 で VM を作って使う」。どちらも、2 冊にあったときからのもの）だけ `#####`
   - 手順（番号付きリスト）を持つ見出しを、階層によらず「項」と呼ぶ。本文では「この項の手順 N」と書く
   - 見出しに「（任意）」を付けない。用途の主の導入の手順は `### <用途>` の直下に置き、「<用途>: 実施手順」「<用途>: Windows 11 で使う」の見出しは作らない
   - `##` カテゴリは 1 行の箇条書きのリードだけで、手順を持たない。例外は `## 更新`（どの更新をどの項で行うかの案内を残す）
   - カテゴリと用途は、新しく入れた PC で上から選んで通しても、前提の項が先に来る順に並べる
   - `---` は、各 `###` 用途のまとまりの末尾にだけ置く
1. **どの項も単独で通せるようにする。** 項のリードは「何をするか → `- 前提: …` → `- 実行場所: …` → そのほかの箇条書き → アラート」の順にする
   - 前提は、先に通しておく項へのリンクで書く（無ければ `- 前提: 無し`）。冒頭の全体の前提は繰り返さない。子の項の前提は、その用途の導入を済ませる項（親が手順を持たなければ、導入の兄弟の項）にする
   - 実行場所は、ホスト・ユーザー・シェル・窓（Windows は管理者か通常の Windows PowerShell 5.1 か、Git Bash か）を書く。冒頭の既定と同じでも書く
   - 前提は `[!IMPORTANT]` に入れず、箇条書きにする。`[!IMPORTANT]` は、項全体にかかわる権限・実行場所の注意だけにする
   - 変数は、それを使う項ごとに手順 1 で設定する（ほかの項の変数に頼らない）。同じ値にする変数は、どの項と同じ値かを箇条書きに書く。自動で取れる値は同じ式で取り直す
   - windows-setup.md では、窓を開く手順の無い項は、手順 1 で窓を開き、変数を設定する手順は手順 2 にする
   - 「この窓」「続けて」「前の項で開いた」など、ほかの項の状態に頼る書き方をしない。代わりの導入がある項は、リードに分岐を書く（almalinux-setup.md の「Homebrew」）
   - 複数の項をまとめて確かめる項（almalinux-setup.md の「再起動と確認」、windows-setup.md の「再起動の後に確かめる」）は、確かめる項をリードの前提に並べ、ほかの項に依る確認に「（[X](#x)を通したとき）」を付ける
1. 冒頭のリードは、全体に共通する前提（対象 OS・ユーザーと権限・貼り方・「確認」の読み方・記録へのリンク）と、「どの項も単独で通せる。目的の項のリードの前提を先に満たす」「新しく入れた PC では、カテゴリを上から順に、要る項を選んで通す」だけにする。項の範囲で窓や貼り先を割り当てる書き方・「上から順に通す」・省略できない手順の一覧は置かない

各用途の手順は次の骨格に揃える（2 冊は、上の「2 冊の骨格」が優先する）。

1. （ai-agents.md など）導入前の任意節を除き、タイトルの直後に `## 実施手順` を置き、手順はその中の**番号付きリスト 1 つ**で振る（`### 1. 〜` のような番号付きの見出しにしない）。マーカーは手順以外のリストも含めてすべて `1.` にし、番号は自動で振らせる。手順番号は 1 から数える（変数ブロックがあればそれが手順 1）。各手順は下の「手順の形」に揃え、本文は 3 スペース字下げにする。**前半は読者が実行する操作と、その場で必要な短い注意だけ**にする
   - **手順が 15 を超える節は、内容のまとまりで `###` の見出し（以下「項」）に分け、手順番号は項ごとに 1 から数える**（2026-10-10 に 11 節を 62 項に分けた。ほかの手順書からその手順へリンクで飛べるようにするため）
     - 分けた節（2026-10-10。2 冊は、2026-10-14 にカテゴリ別に組み直す前の名前）: almalinux-setup.md と windows-setup.md の実施手順・extra のロールバック、windows-setup.md の任意節「表示・入力・音・ストレージを変える」、両正本の Forgejo・WireGuard・VirtualBox・GNOME のデスクトップ共有・Hyper-V・VMware の実施手順、ai-agents.md の「Grok Build のブラウザ操作」の実施手順、WireGuard の「AlmaLinux 10 の PC からつなぐ」と「Windows 11 で使う」（2026-10-11 に統合するまでは、wireguard-road-warrior.md の実施手順と Windows 11 で使う）
     - 項は 2〜15 手順にする。項の中も番号付きリスト 1 つで、マーカーは `1.`。節のリードは最初の項の前に置き、項の見出しの直後は手順から始める
     - 項の見出しには番号を入れず、同じファイルのほかの見出しとアンカーがぶつからない名前にする。既存の名前は維持する。集約する見出しにはツール名を付け、旧→新のアンカー対応を記録する
     - 2冊に同名の見出しがあったものを 1 冊へ移すときは、AlmaLinux 10 側の名前を保ち、Windows 11 側の名前に「Windows 11 で」を付ける（ai-agents.md の「Claude Code」と「Windows 11 で Claude Code を入れる」）
     - 変数ブロックは、それを置いた項の手順 1 になる（ai-agents.md の「Claude Code」「Windows 11 で Claude Code を入れる」など）。2 冊では、変数を使う項ごとに手順 1 に置き、windows-setup.md で窓を開く手順のある項は手順 2 にする（2026-10-14 から。それまでは almalinux-setup.md の「システムの設定」の手順 1・windows-setup.md の「PC 全体の設定」の手順 2 の変数を、後ろの項でも使っていた）
1. 手順ごとの実測・出力例・検証の経緯は `docs/verification/<手順書名>.md` に、理由・比較・背景は `docs/reference/<手順書名>.md` に置く。検証記録は非公開の `ryo-aoki-pc/setup-notes-verification` の同じパスにある。対応する節と手順番号を見出しに含める（項に分けた節は `### <節> / <項> / 手順 N: 補足: <題>`）。操作に必要な分岐・失敗時の対処・短い注意は手順書に残す
1. 環境固有の値は手順冒頭の変数ブロックまたは `site.env` だけで設定する（`${SERVER_IP}` 形式。値の置き場所は、2 冊は項ごと、ほかの文書は用途ごとに 1 か所）。**変更が必須の変数は 1 変数ずつのコードブロックに分け、変更が任意の変数（既定のままでよい・自動で入るが違えば直す）は 1 つのブロックにまとめて必須ブロックの後に置く。** 値の読み戻しは任意の変数のブロックの末尾に入れる。シェルに貼って編集する手間を減らすため
   - **変える必要の無い値は変数にせず、コマンドに直接書く。** 固定の URL・パス・パッケージ名、ツールが既定の場所からしか読まないパス（`~/.config/bat/config` など。変数を変えても読み込み先は変わらない）、動作確認にだけ使う名前、`${USER}` や `$(uname -m)` の言い換えがこれに当たる
   - 変数が 1 つも無い文書には変数の手順を置かず、手順 1 から主題を始める
1. 動作確認を含む実行手順を `## 実施手順` の番号付きの手順にし、任意設定・設定ファイル・更新は `## 実施手順` の後ろの `##` 見出しに置く。ここまでが前半（2 冊は、用途の導入を `### <用途>` に、設定ファイル・ほかの設定・使い方・更新を子の `####` に置く）
   - **`## ロールバック`（または「全部消す」）・`## Windows 11 のロールバック`・ロールバックを広げる節（extra/forgejo.md の「保持したデータも削除する（任意）」）・`## 注意点` は、`docs/extra/<手順書名>.md` に元の順で置く**（2026-10-10 に 49 本の本体から移した。ふだん見ない箇所を本体から外し、本体を短くするため）。手順の外の節を足すときも、ロールバックか注意点なら extra に置く
   - extra の冒頭は、タイトル（`# <手順書のタイトル>のロールバックと注意点`。片方しか無ければ「のロールバック」「の注意点」）→ 正本の該当用途・検証記録・参考資料への案内 → 手順番号の参照先の説明にする。削除済みの旧文書にはリンクしない。正本の用途節のリードと、参考資料・検証記録の冒頭から extra へ案内する
   - extra の手順も同じ「手順の形」で書く。現在の手順参照には、正本の該当項の名前と手順番号を付ける。過去の番号・文書単位の説明は当時のものとして保持する
   - **後ろの節も、貼るコマンドか読者が行う操作があれば同じ形の番号付きリストにする**（節ごとに 1 から数える。コマンドの無い操作は下の「手順の形」）
   - 節の中の並びは「リード（短い箇条書きとアラート）→ 番号付きリスト → `---`」にし、リストの後ろには何も置かない
   - 操作の無い参照の節（表だけの「使い方の基本」など）はリストにしない
   - `##` 見出しは既存の参照を保つ。集約する見出しの変更は対応表と参照元のリンクを合わせる。旧原文への参照は移動元コミットに固定する（extra へ移した見出しも名前は変えず、リンクの先だけを `extra/x.md#…` に直した）
1. 手順書に検証記録や一般的な背景説明の `## 補足` は置かない。検証記録には「対象と検証環境」「実施前の状態」「完了時点の状態」「付録（検証記録）」を置き、参考資料には「選択した方針」「参照」や構成の説明を置く。注意点に実測と操作が混ざる場合、操作・対処は手順書に残し、元の実測は検証記録で保持する
1. **共有する前提も正本の項・節に置く。** 使う側から項を名指しする。同じコマンドを両 OS の同じ実行環境で使える場合だけ一か所へ集約し、もう一方から参照する
   - PowerShell・dnf・scoop など OS ごとに異なる操作は各 OS の手順に置く。実行するホスト・ゲスト・シェルを明記する
   - 参照先は一まとまりの項を通せる形にする。細かな番号を飛ばす必要があれば、共通操作を独立した項へ分ける
   - 個別リポジトリには正本への案内を置き、導入操作を重複して保守しない
1. 対話入力（パスワード、`[y/N]`、エディタ・TUI・GUI の起動、再起動）があるコマンドは、**その手順の最後のコマンド**にする。後ろに続くコマンドは次の手順に分け、止める手順の最後の箇条書きを「**次の手順は、〜してから貼る**（続けて貼ると〜として食われる）」にする。続けて貼ると後続行が入力として食われるため。`sudo` はパスワードを聞かない設定（NOPASSWD）を前提に書き、`sudo` のパスワードに答えるための止める箇条書きや、そのためだけの手順の分割は置かない
1. **冒頭は全体に共通する前提だけにする。** 対象 OS・実行場所・ユーザーと権限・貼り方・「確認」の読み方・記録へのリンクを短く書く
   - GUI・対話入力・条件付き操作の全手順番号一覧と、本文を繰り返す用途索引は置かない。切り替え・分岐・停止は該当手順に書く
   - 項や節を単独で通す読者のため、各項・各節のリードに必要な前提と実行前警告を置く（2 冊は、上の「2 冊の骨格」の 2 の「- 前提:」「- 実行場所:」）。ある項のデスクトップ限定などの条件を、ほかの項へ広げない

### 手順の形

手順（`## 実施手順` と、その後ろの節の番号付きリストの項目。2 冊は、すべての項の番号付きリストの項目）は、次の 3 つをこの順に置く。extra のロールバックにも同じ順を適用する。コマンドの無い手順（下の「コマンドの無い操作」）は、コマンドを除いた 2 つを置く。

````
1. 1 行の説明。

   ```bash
   操作のコマンド
   printf '\n\033[7m 確認 \033[0m\n'   ← 出力を確かめるブロックだけ（下の「確認の見出し」）
   確認のコマンド
   ```

   - 確認・分岐・注意（補足。表示する）
   - **次の手順は、〜してから貼る**（続けて貼ると〜として食われる）   ← 止める手順だけ

````

- **1 行の説明**
  - 太字にしない 1 文で、「〜する。」で終える（目安は 60 字まで）
  - 実行する場所・条件・前提はここに書く（「WG ホストで、公開鍵を登録する。」「Secure Boot が有効なときだけ、署名鍵を登録する。」）
  - 変数の手順は「変数を設定する（`SERVER_IP` は必ず値を入れる）。」のように、必須の変数を括弧で示す
- **コマンド**
  - 説明の直後に置き、ブロックの間に何も挟まない。コマンドの無い手順には置かない
  - コマンドのある手順では、箇条書きを最初のコードブロックより前や、複数のコードブロックの間に置かない。確認・分岐・注意の箇条書きは、最後のコードブロックの後ろにまとめる
  - 並べてよいのは「1 変数だけのブロック（0 個以上）→ ほかのブロック 1 つ」だけ
  - **ai-agents.md では、フェンスの行を除いて 20 行以上のコードブロックを `<details>` で折りたたむ**（2026-10-14。利用者の決定。長いブロックで手順の説明と確認の箇条書きが離れるのを避ける）
    - 書式は、`<details>` の行、`<summary>貼るコマンド（PowerShell・50 行）</summary>` の行、空行、コードブロック、空行、`</details>` の行。括弧の中は言語（`PowerShell` か `bash`）と、フェンスを除いた行数の実数
    - `<details>` と `</details>` の行は、手順の本文と同じ 3 スペース字下げにする。`<summary>` の行は、それより 2 スペース深い 5 スペース字下げにする。`</summary>` の後ろと `</details>` の前後には空行を置く
    - `<summary>` を 2 スペース深くするのは、Neovim の Markdown の整形（[LazyVimStarter](https://github.com/ryo-aoki-pc/LazyVimStarter) の `glfm_markdownlint`）が HTML をタグの入れ子に合わせて字下げし、保存のたびに書き換えないようにするため（2026-10-15。利用者の決定）
    - 空行が無いと、GitHub はコードブロックを地の文として出し、中の `<...>` を消す。字下げが無いと番号付きリストが切れ、次の手順が 1 に戻る
    - `<summary>` に Markdown の記法や `<...>` を書かない。折りたたみのタグは、説明とブロックの間・ブロックと箇条書きの間に挟んだものとして数えない
    - 変数のブロック、手で打つ `text` のブロック、1 行の説明に「（取り戻せない）」とある手順のブロックは、20 行以上でも折りたたまない
    - 何をするブロックかは、1 行の説明だけで分かるように書く。リードで「折りたたまれたブロックは、開いてからコピーボタンで写す」と案内する
    - ほかの文書には広げない
  - 言語は bash。手で書き足す設定の断片（lazygit の yaml など）だけは、その言語のブロックでよい
  - Windows の操作は `powershell` のブロックにし、Windows PowerShell 5.1 で貼る。管理者が必要な操作は該当項で指定する
  - Git Bash・WSL・別ホストの bash を使う操作は、貼り先を説明で明記する。共通 CLI の同一ブロックを参照するときもシェルを指定する
  - 貼り付け設定前の conhost は Ctrl+V を使う。scoop の導入は管理者ではない窓で行い、SSH の昇格済みセッションには貼らない
  - PowerShell の変数が空ならブロック先頭で中断する。`}` と `else` / `elseif` は同じ行に置く
  - windows-setup.md の「Windows と AlmaLinux のデュアルブート」の手順 4・5 は、Windows のセットアップのコマンド プロンプト（diskpart）に手で打つ（貼れない）ので、`text` のブロックに 1 行ずつ書く。値（ディスクの番号・大きさ）は変数にできないのでコマンドに直接書き、変える値を箇条書きで名指しする（変数ブロックと `<...>` の規則の例外）
  - Windows Sandbox の状態確認・有効化・無効化・再起動は管理者の Windows PowerShell 5.1、起動・試験・窓を閉じた後の確認は通常のデスクトップで行う
  - 初期設定の「Git」は例外で、Windows でも Git for Windows の Git Bash に AlmaLinux 10 と同じ `bash` のブロックを貼る（PowerShell 向けに書き分けない。shell-terminal.md の「Git Bash と WezTerm の設定」の手順 4 が、almalinux-setup.md の「Git」の手順 1〜10 を名指しする）。Git for Windows を入れる項（windows-setup.md の「Git for Windows」）だけは PowerShell のブロック。windows-setup.md の「git-delta」の手順 4 と shell-terminal.md の「シェルのツールを入れる」の手順 7・8 も、Git Bash（WezTerm のタブ）で AlmaLinux 10 の手順（almalinux-setup.md の「git-delta」の手順 1・3、shell-terminal.md の「シェルのツール」の手順 4〜7・9・10 と「キー操作を試す」の手順 2〜5）を名指しする、コマンドの無い手順にする（bash のブロックを書き写さず、Windows との違いだけを箇条書きに書く）
  - `<...>` を含む別マシン用のコマンドは、ブロックにせず箇条書きのインラインコードにする
  - `sudo` の後ろに別のコマンドが続くブロックは、全体を `{` と `}` の行で囲む（中は 2 スペース字下げ。ヒアドキュメントの本文と終端の行は字下げしない）。手順の外の節や tool-catalog.md のブロックも同じ
    - ブラケットペーストが効かないときに貼ると、`sudo`（1.9.17 の `use_pty`）が端末に残った行を読んで捨てる（NOPASSWD でも捨てる。実測は [samba-client.md の付録](https://github.com/ryo-aoki-pc/setup-notes-verification/blob/main/docs/verification/samba-client.md#付録-sudo-の後ろの行が失われる条件2026-09-28)）
    - bash は `}` まで読んでから実行するので、捨てられる行が残らない。変数の空を弾くブロックは `if … fi` でもよい（samba.md の「Samba クライアント」）
    - 目視で確かめてから次を実行するもの（dry-run の後の本番など）は、囲まずに手順（手順の外ならブロック）を分ける
    - 点検は、ブロックを bash が 1 回に読む単位（`bash -n` が通る最小の行のまとまり）に区切り、`sudo` を含む単位の後ろにコメント以外の行が残らないかで見る
  - 変数が空なら止めるのは、ブロックの先頭の `if [ -z "${VAR}" ]; then echo '中断: …' >&2; else … fi` で行う。ヒアドキュメント・パイプ・`$(…)` の中の `${VAR:?}` は、そのコマンドしか止めず、後ろの行は動く（almalinux-setup.md の検証記録にある、もとの gnome-power.md 手順 3 の補足、「Samba クライアント」）。`{ … }` で囲んでも同じ
- **確認の見出し**（2026-10-10）: 貼ったコマンドの表示と、確かめる出力を見分けるため、成功条件で出力を確かめるブロックには、判定する出力を出す最初のコマンドの直前に、反転表示の「確認」を出す 1 行を置く
  - `bash` は `printf '\n\033[7m 確認 \033[0m\n'`、`powershell` は ``"`n$([char]27)[7m 確認 $([char]27)[0m"``（ほかの行と同じ字下げ）
  - ブロック全体が確認ならブロックの先頭（`{` で囲んだブロックは `{` の次の行）、変数ブロックは読み戻しの直前。判定する出力が操作のコマンド自身の出力なら、そのコマンドの直前
  - 置かないもの: 1 行だけのブロック、確かめる出力の無いブロック、`text` などのブロック。ヒアドキュメント・`$(…)`・パイプや `&&`・`||`・行末の `\`（PowerShell は `` ` ``・`|`・`,`・`=`）の続き、`$?`・`$LASTEXITCODE` を読む行の直前、`if` の条件の中、関数の定義と代入の式の中にも置かない
  - PowerShell は `Write-Host` にせず、パイプラインに出す文字列にする（Windows PowerShell 5.1 の表の出力は 300 ms 待ってから出るので、`Write-Host` の見出しが前の出力より先に出る）
  - 足したのは表示のための 1 行だけで、実機では流していない（検証範囲は変えない）。bash は `bash -n`、PowerShell は Linux の pwsh 7.4.6 の構文解析と、見出しが独立した文になっていることを確かめた。Windows PowerShell 5.1 の conhost で反転表示になることは未確認
  - 箇条書きの成功条件は、この見出しの後ろの出力で判定する。手順書のリードの「貼った後は、反転表示の「確認」から後ろの出力を箇条書きで確かめる」で案内する
- **確認・分岐・注意**
  - 箇条書きだけにする（入れ子は可）。段落・表・コードブロックは置かない
  - **置くのは次のものだけ**（2026-10-10 に全手順書をこの規則で絞った）: 成功条件（エラーに見えて正常な出力を含む）／中断（「〜なら中断する・進まない・やり直す」と失敗の表示）／読者の操作が変わる分岐／止める箇条書き（「次の手順は、〜してから貼る」「後ろの節…」）／操作そのもの（対話の答え方、コマンドの無い手順の画面の順やキー、控える値とその使い先）／危険の注意（秘密を載せない、取り戻せない、SSH や RDP が切れる、公開の範囲など）
  - 理由（〜ため・〜なので）・値や出力の意味・ブロックの動き・仕組み・既定値・経緯・操作を変えない副作用は、参考資料の `## 補足` の `### <節名> / 手順 N: 補足: <題>` に置く。条件と理由が混ざるときは、条件を手順書に残し、理由だけを移す
  - ほかの文書から「手順 N の補足」「手順 N の箇条書き」と名指しされている箇条書きは、手順書に残す
  - 実測の出力例は検証記録へ移し、箇条書きには判定に要る成功条件だけを書く
  - 「次のブロック」「上の 2 つのブロック」のような位置の言い方はせず、手順番号で言う
- **検証記録・参考資料**: 操作の節と手順番号を示し、手順書から参照する。手順書に折り畳んだ背景や実測を置かない（折りたたんでよいのは、上の「コマンド」の、貼るコードブロックだけ）
- **手順を分けるところ**
  - 止める箇所（上の骨格の対話入力、完了待ち、目視の確認）
  - 別のホストや端末で行う操作
  - コマンドの無い操作（下）
  - 条件付きの操作（「〜なら」「〜ときは」「〜も消すなら」）
  - 別々の操作や確認（太字の小見出しで区切るような）
- **ブロックをまとめるところ**
  - 条件の無いつなぎの文（「値を読み戻して確かめる」「次に〜を確かめる」）だけで分かれるブロックは、コマンドを変えずに 1 つにつなぐ
  - ただし、新しいシェルで貼り直す変数のブロックには、読み戻し以外のコマンドを足さない（貼り直すたびに実行されるため）
- **条件付きの手順**
  - 条件は 1 行の説明に書く。1 つの条件が複数の手順にかかるなら、それぞれに書く
  - 判定する手順の最後の箇条書きに「〜なら、手順 N は飛ばす」と書く
  - 代わりに行う手順は「（この節の手順 1 の代わりに）」と書く。元に戻す手順は最後に置き、「元に戻すときは、」で始める
- **コマンドの無い操作**は、独立した番号付きの手順にする（コマンドのブロックを置かず、1 行の説明 → 確認・分岐・注意の箇条書き）
  - 当たるもの
    - 画面の操作: GUI、ブラウザ（ログイン・リンクの承認・Web の設定）、起動途中の画面（MokManager）、VM のウィンドウのメニュー
    - 別のマシン・端末・機器での操作: ルーター、スマートフォン、相手のデバイス、LAN の外へのつなぎ替え、別のマシンにファイルを置く
    - 自分で行う切り替え: ログアウトしてログインし直す、アプリや VM を閉じる、閉じて起動し直す
  - 1 行の説明に、どこで何をするかを書く（「VM のウィンドウのメニューで、Guest Additions の CD を入れる。」「ブラウザで URL を開き、この PC を Dropbox に接続する。」）。メニューの順や押すキーは箇条書きに書く
  - `<...>` を含む別マシン用のコマンドは、箇条書きのインラインコードにする（上の「コマンド」）
  - 「**次の手順は、〜してから貼る**」は、次にコマンドを貼る手順の直前（コマンドの無い手順）の最後に置き、その前のコマンドの手順には置かない
  - 次のものは手順にせず、その手順の箇条書きに書く
    - その手順のコマンドが開いた対話への入力: パスワード・`[y/N]`・エディタ・TUI・開いたウィンドウ・`ssh` や `distrobox enter` の先のシェル（上の骨格の対話入力と同じく、「次の手順は、〜してから貼る」で止める）
    - コマンドが起こしたことの完了待ち（`sudo systemctl reboot` の後に起動してログインし、新しい端末を開く、など）
    - 同じ操作を画面から行う別の方法（「アプリ一覧からでも同じ」）
    - 前提を直して始め直す案内（「〜なら、UEFI で有効にしてから始める」）、任意の後片付け（「要らなければ手で消す」）、次の手順に貼る値の受け渡し（公開鍵の 1 行）
- **手順の参照**
  - 2 冊では、手順はいつも項の名前を付けて指す（同じ文書の中は `[<項>](#<アンカー>)の手順 N`、項の中は「この項の手順 N」。下の「項に分けた節の手順」と同じ）
  - （2 冊以外）手順には見出しのアンカーが無いので、リンクは `[手順 N](#実施手順)`（別文書は `[x.md 手順 N](x.md#実施手順)`）にする。`## 実施手順` の中ではリンクにせず「手順 N の補足」「この手順の補足」と書く
  - **項に分けた節の手順は、項の名前を付けて指す**（項の名前の無い「手順 N」は書かない）
    - 同じ項の中: 「この項の手順 N」（リンクにしない）
    - 同じ文書の別の項: `[<項>](#<アンカー)の手順 N`（リンクにする）
    - ほかの文書から: `[<文書>の「<項>」の手順 N](x.md#<アンカー)`。2 つの項にまたがる番号は、項ごとのリンクに分ける
    - リンクの無い参照（コードの中のメッセージ・検証記録・AGENTS.md と `docs/dev/` の本文など）: 「<文書>の「<項>」の手順 N」。同じ文の中で直前に名前を出した項は「同じ項の手順 N」でよい
    - 項をまたぐ範囲は、項の名前を並べて書く（windows-setup.md の中なら「`[PC 全体の設定](#pc-全体の設定)から[WSL と再起動](#wsl-と再起動)までの手順`」）
  - 2 冊以外の、項に分けていない文書では、単に「手順 N」と書いたら `## 実施手順` の手順を指す。後ろの節の手順は、その節の中では「この節の手順 N」、ほかからは `[ロールバック](extra/x.md#ロールバック)の手順 N` と書く（ロールバックは extra にある）
  - 手順を分けたりまとめたりしたら、本文・検証記録・参考資料・リードの `> [!IMPORTANT]`・ほかの文書・AGENTS.md と `docs/dev/`・`scripts/wireguard/` のヘッダコメントにある番号を付け替える。検証の記録（状態行・付録）は同じコマンドを指すように付け替え、範囲を広げない

### 表現の規則（箇条書きとアラート）

- **手順の本文は「操作 → 確認」だけにする。** コマンドの後は箇条書き（1 項目に 1 つの事実。末尾に「。」を付けない）だけにし、実測は検証記録へ、理由・背景は参考資料へ移す。手順書の箇条書きも目安は150字以内。長い項目は必要な判断を残して縮め、理由や実測を記録へ移す
- **アラート（`> [!NOTE]` など）は本文の最上位にだけ置く。** GitHub は番号付きリストの中のアラートを描画しない（公式ドキュメントの「Alerts cannot be nested within other elements」）。手順の中の注意は `- **注意**: …` の箇条書きにし、複数の手順にかかわる注意はリードのアラートにまとめる。`## 実施手順` の後ろの節の手順にかかわるアラートは、その節のリードに置いて手順を名指しする（「**この節の**手順 3 で〜」）
  - 実行前に読む必要がある警告は、1 手順だけにかかわる場合も対象の節のリードに置き、節・項の名前と手順番号を示す。箇条書きの順序を直すために、警告を危険なコマンドの後ろへ移すだけの修正はしない
- 使い分け:
  - `[!IMPORTANT]`: リードの前提（上の骨格の最後の項目。OS で節を分けた手順書は、`## Windows 11 で使う` のリードにも置く）。2 冊では、前提は `- 前提:` の箇条書きにし、`[!IMPORTANT]` には項全体にかかわる権限・実行場所の注意だけを置く
  - `[!WARNING]`: 複数の手順にかかわる危険（wireguard.md の「WireGuard」の `apply` の restart で ssh が切れる、など）、手順の外の節（任意設定・更新・ロールバック）や、2 冊の項で事故につながる注意（同期対象にホームを丸ごと入れない、など）
  - `[!CAUTION]`: 取り戻せない削除（鍵・デバイス ID・プロファイル・パスワード DB・Homebrew 全体など）をする手順のある節の、リスト直前のリード。どの手順かを名指しし、その手順の 1 行の説明にも「（取り戻せない）」と書く。軽い設定ファイルの削除には付けない
  - `[!NOTE]`: 検証記録の「対象と検証環境」の注記（変数表・プレースホルダ・秘密情報）
  - `[!TIP]` は使わない。1 用途の節（2 冊は `###` 用途のまとまり）に 5 つまでにし（extra は手順書と別に数える。OS で節を分けた手順書は OS ごとに数え、両 OS に共通の節のものは両方に数える）、アラート同士を空行だけで続けて置かない
- **検証記録の「状態」行は入れ子の箇条書きに割る**（何を通したか・確認したこと・確認していないこと）。「選択した方針」「注意点」なども、150 字を超える段落は箇条書きに割る。過去の検証記録（付録を含む）は書き直さない。分離・移動では実施日・対象版・出力・成功と失敗・未実施範囲を保持し、相対リンクや見出しの移動に必要な変更だけを行う（過去の手順番号は当時のものとして保持し、集約対応表で現在の節と対応させる）
- **太字の `**` を約物に接して閉じない。** 閉じの `**` の直前が `）`・`。`・`` ` `` などの約物で、直後が文字だと太字にならない（CommonMark の規則。`**最新版（Rapid Release）**を` は記号のまま出る）。約物を太字の外に出すか、太字の後ろを約物か空白にする
- **状態（検証範囲）を変えたら**、対応する検証記録の状態行と `docs/dev/structure.md` のその文書の項を合わせて直す。新たな検証をしていない文書分離では、検証範囲を変更しない
- **このリポジトリの `docs/images/<手順書の名前>/` には、手順書・参考資料に貼る画像だけを PNG で置く**（今は Forgejo の `*-en-v16.png` と AI エージェント）
  - 検証で撮った画面は非公開側の `docs/images/<手順書の名前>/` に PNG で置き、検証記録から相対パスで指す（今は Windows のデュアルブート・GNOME のデスクトップ共有・AlmaLinux の初期設定・AlmaLinux の VM・VirtualBox・Forgejo）
  - 実施に必要な判定条件は手順書の箇条書きに残す
  - 同じリポジトリの中では、既存の画像ファイルは移動せず、文書側の相対パスを直す
  - **手順書に貼るのは、コマンドの無い手順で、どこを押すか・何が出れば成功かを画面で示すものに限る**（2026-10-14。利用者の決定）。その手順の最後の箇条書き（「次の手順は、〜してから貼る」があれば、その直前）に 1 枚まで置く（almalinux-setup.md の「Forgejo: 使い方の基本」、ai-agents.md の「Grok Build のブラウザ操作」）
    - 節のリードで、何で撮ったか（実機か VM か、対象の版）と、画面内の値が試験用であることを断る
    - ai-agents.md の画像は `docs/images/ai-agents/<主題>-<内容>-v<版>.png` とし、幅は 1440 px までにする
    - 入力済みの認証欄、URL のセッション ID、QR コード、証明書の画面（名前に PC 名が入る）も載せない
  - 何で撮った画面か（VM か実機か）を断る。窓の部分だけを切り出す
  - 本当のユーザー名・ホスト名・IP が写るものは載せない（試験用の値にして撮る）
  - 画像の説明（`![…]`）には、画面で判定に使う文字を書く

`docs/tool-catalog.md` は手順書ではなく一覧なので、この骨格（`## 実施手順`・変数ブロック・番号付きの操作手順）に従わない。調査日と検証範囲は非公開側の `docs/verification/tool-catalog.md` に置き、表の各行に確認の深さ（起動 / 導入 / メタデータ）を書く。表に載せる導入コマンドはコンテナなどで実行したものだけにし、実行していない行はコマンドを書かない。プレースホルダと秘密情報の規則はそのまま適用する。

出力例・ログ・表の中の値は `<HOSTNAME>` / `<SERVER_IP>` などのプレースホルダで書き、実測出力は変数に置き換えない。`<...>` を含むコマンドは bash のコードブロックに置かず、読者が値を入れるブロックは先頭で変数が空なら中断させる（README「記法」）。手順書のコードブロックは検証目的でも実機で機械的に実行しない。コマンドは実際に実行したものを載せる。パスワード・鍵・トークンは private でも書かない。
